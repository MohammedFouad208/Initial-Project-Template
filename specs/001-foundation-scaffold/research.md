## Research Questions & Decisions

### R-001: Project Layout — flat vs. nested `src/` wrapper

**Question**: Should the four projects sit at the solution root (flat) or be nested inside a `src/` folder?

- **Decision**: Flat layout — all four projects sit directly at the solution root alongside the `.sln` file.
- **Rationale**: Package Manager Console in Visual Studio resolves the default project by selecting from the top-level `.csproj` targets. A flat layout avoids path-resolution issues with `Add-Migration` (which requires specifying `-Project` and `-StartupProject` explicitly when nested). The flat structure is also the default generated by Visual Studio's "Add New Project" wizard, reducing friction for new contributors.
- **Alternatives considered**: `src/` nested layout — rejected because PM Console migration commands become more verbose and error-prone (`-Project AdminTemplate.Infrastructure -StartupProject AdminTemplate.Web`); the spec mandates PM Console as the only migration tool.

### R-002: BaseEntity Design — abstract class vs. interface

**Question**: Should `BaseEntity` be an abstract class (inheritable) or an interface?

- **Decision**: Abstract class with Id (`Guid`) and `CreatedAt` (`DateTime`) properties.
- **Rationale**: `ApplicationUser` and `ApplicationRole` already extend IdentityUser/IdentityRole (sealed inheritance chain from Identity), so they cannot also inherit `BaseEntity`. `BaseEntity` is used only by `RolePermission` and any future non-Identity entities. An abstract class allows default property initialization (`CreatedAt = DateTime.UtcNow`) and EF Core convention mapping without extra configuration. Interface approach would require each entity to duplicate property declarations.
- **Alternatives considered**: Interface `IBaseEntity` — rejected because it provides no default implementation and forces boilerplate on every entity. Value object or record — rejected as overly complex for simple auditing fields.

### R-003: Identity Extension Strategy — shadow properties vs. subclass

**Question**: How should `FullName`, `IsActive`, and `CreatedAt` be added to the Identity user/role tables?

- **Decision**: Subclass `IdentityUser<string>` as `ApplicationUser` and `IdentityRole<string>` as `ApplicationRole`, adding the extra properties directly.
- **Rationale**: Subclassing is the official ASP.NET Core Identity pattern for extending the user/role tables. It keeps all user properties on a single table (no joins), EF Core maps them automatically, and the Identity APIs (`UserManager<ApplicationUser>`) carry the extended type throughout the app with full type safety. Shadow properties would be accessible only through EF Core queries and cannot participate in Identity API validation.
- **Alternatives considered**: Shadow properties via `modelBuilder.Entity<IdentityUser>().Property<string>("FullName")` — rejected because they are invisible at the application layer and cannot be used by UserManager. Separate profile tables (1:1 join) — rejected as unnecessary complexity for a template with a small attribute set.

### R-004: RolePermission Primary Key — int vs. Guid

**Question**: Should `RolePermission.Id` use `int` (auto-increment) or `Guid`?

- **Decision**: `Guid` generated by the application (`Guid.NewGuid()`), set via the entity constructor or property initializer.
- **Rationale**: Consistent with distributed-friendly design; no SQL Server sequence dependency means the entity Id is available before hitting the database (useful in seeding logic). `BaseEntity` declares Id as `Guid` to establish a consistent convention for all future non-Identity entities.
- **Alternatives considered**: `int` identity — rejected because it creates an implicit dependency on the database sequence for entity identity, making in-memory seeding logic slightly more complex. Composite PK (`RoleId` + `ObjectName` + `FunctionName`) — considered as a natural key, but rejected because EF Core navigation and delete cascades are simpler with a surrogate Guid PK.

### R-005: Seeder Trigger Point — Startup vs. Migration vs. Background Service

**Question**: Where and when should the data seeder execute?

- **Decision**: In `Program.cs` after `app.Build()`, using `IServiceScope` to resolve `DataSeeder` from DI, executed synchronously before `app.Run()`.
- **Rationale**: Running at startup (before `app.Run()`) guarantees the seed completes before the first HTTP request is served. Using `IServiceScope` correctly respects the DI lifetime scoping rules for `DbContext` (which is scoped). This pattern is the Microsoft-recommended approach in the EF Core documentation for seeding with `UserManager`/`RoleManager`.
- **Alternatives considered**: EF Core's built-in `HasData()` seeder — rejected because it cannot use `UserManager` (which hashes passwords correctly) and cannot resolve scoped services. Background hosted service — rejected as unnecessarily complex for a sequential startup operation; race conditions with first requests are undesirable.

### R-006: Global Authorization — `RequireAuthenticatedUser` vs. per-controller `[Authorize]`

**Question**: How should the default "all admin routes require authentication" policy be implemented?

- **Decision**: Register a global `AuthorizationPolicy` via `builder.Services.AddAuthorization(options => options.FallbackPolicy = new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build())` in `Program.cs`. Individual public routes (login, register, static assets) use `[AllowAnonymous]`.
- **Rationale**: A global fallback policy ensures that any new controller or action is secure by default — a developer must explicitly opt out with `[AllowAnonymous]`. This "secure by default" approach aligns with the constitution's security mandate and eliminates the risk of forgetting `[Authorize]` on a new controller. Per-controller `[Authorize]` attributes are prone to omission errors.
- **Alternatives considered**: `[Authorize]` on every controller — rejected because it relies on developers remembering to apply the attribute. Middleware pipeline `UseAuthorization` without a fallback policy — rejected for the same reason.

### R-007: Repository Interface Scope — Read-only vs. full CRUD in Phase 1

**Question**: Should the repository interfaces in Phase 1 be full CRUD or just the signatures needed for Phase 1 (seeding/startup)?

- **Decision**: Define full CRUD interface signatures in Phase 1 (`GetByIdAsync`, `GetAllAsync`, `AddAsync`, `UpdateAsync`, `DeleteAsync`) even if not all are used until later phases.
- **Rationale**: Repository interfaces live in Domain and are contracts that downstream services depend on. Defining the full surface now means Application service stubs in later phases can reference a stable interface without triggering Domain layer changes. This respects the open/closed principle and avoids circular merge conflicts when multiple phases are worked on in parallel.
- **Alternatives considered**: Minimal interfaces (only what Phase 1 needs) — rejected because changing a Domain interface in Phase 4 would require re-testing Phase 1 deliverables and risks breaking the constitution's dependency direction (Domain should be stable).

### R-008: EF Core Migration Default Project Configuration

**Question**: Which project should be the "default project" for EF migrations in PM Console?

- **Decision**: `AdminTemplate.Infrastructure` as the migration project; `AdminTemplate.Web` as the startup project. Document both in quickstart.md. Standard PM Console command: `Add-Migration InitialCreate -Project AdminTemplate.Infrastructure -StartupProject AdminTemplate.Web`.
- **Rationale**: Migrations must live where the `DbContext` is defined (Infrastructure), but the startup project is needed to resolve `IConfiguration` (connection string) at design time. The Infrastructure project's `InfrastructureServiceExtensions` registers the `DbContext` with the connection string from `IConfiguration`, which is only available when the Web project's `appsettings.json` is loaded.
- **Alternatives considered**: Placing `DbContext` in the Web project — rejected as a clear constitution violation (business/data infrastructure code must not live in Web). Auto-discovery without `-StartupProject` flag — rejected because it is unreliable across Visual Studio versions and IDE configurations.
